# 디자이너-개발자 협업 프로세스

기획자·디자이너·개발자가 화면 하나를 두고도 다른 단어를 쓰는 경우가 잦아 핸드오프 과정에서 혼선이 반복되었습니다. 이 문서는 CommerceHub FE 팀의 협업 규칙을 정리합니다.

## 1. Figma → 코드 핸드오프 절차

1. 디자이너가 Figma에 "Dev Ready" 상태로 프레임을 표시 (색상/간격 등이 Hubkit 토큰과 다르면 이 단계에서 조율)
2. 프론트 개발자는 Figma Inspect에서 값을 직접 베끼지 않고, 아래 3절의 "토큰 매핑표"를 통해 Hubkit 토큰으로 변환
3. Hubkit에 없는 컴포넌트/토큰이 필요하면 개발자가 임의로 만들지 않고, 디자인시스템팀에 신규 토큰/컴포넌트 요청(`#design-system` 채널)
4. 구현 후 Storybook 링크를 디자이너에게 공유해 최종 확인(핀포인트 QA)

## 2. 상태(state) 용어 정리 — 디자인 ↔ 개발

디자이너는 화면 상태를, 개발자는 데이터 상태를 기준으로 이름을 붙이는 경우가 많습니다. 대표적인 매핑:

| 기획/디자인에서 부르는 이름 | Figma 컴포넌트 상태명 | 개발에서의 실제 구현 |
| --- | --- | --- |
| "품절" 뱃지 | `Badge/SoldOut` | `sku.soldOut === true`일 때만 노출 (상품 전체가 아니라 옵션조합 단위, [`../commercehub-be`의 도메인 용어집] 참고) |
| "찜하기 활성" | `IconButton/Active` | 서버 상태(`isWished`)와 낙관적 업데이트(Optimistic Update) 조합. 네트워크 실패 시 원상복구 처리 필요 |
| "로딩중" 스켈레톤 | `Skeleton/ProductCard` | TanStack Query의 `isLoading`(최초 로딩)과 `isFetching`(재검증)을 구분해서 사용 — 재검증 중에는 스켈레톤이 아니라 기존 내용 유지 + 미묘한 로딩 인디케이터만 표시 |
| "비활성(disabled) 버튼" | `Button/Disabled` | 단순 스타일이 아니라 실제 `disabled` 속성 적용 + 접근성 상 이유 텍스트 제공(스크린리더 대응) |

## 3. 디자인 토큰 매핑

Figma 변수(Variables)와 Tailwind/Hubkit 토큰은 이름이 다를 수 있습니다. 신규 화면 작업 전 아래 매핑표를 확인합니다.

| Figma 변수명 | Hubkit/Tailwind 토큰 |
| --- | --- |
| `color/brand/primary` | `text-brand-500` / `bg-brand-500` |
| `color/text/default` | `text-gray-900` |
| `spacing/section` | `py-16` (섹션 간 기본 여백) |
| `radius/card` | `rounded-xl` |

토큰이 매핑표에 없으면 임의 값을 쓰지 말고 디자인시스템팀에 확인합니다.

## 4. 리뷰 문화

- 디자인 관련 PR 코멘트는 "이게 맞나요?"보다 Figma 링크 + 스크린샷을 함께 남겨 비교하기 쉽게 합니다.
- 픽셀 단위 차이는 디자이너가 직접 Figma Inspect로 확인 후 코멘트하며, 개발자는 임의로 "비슷하니 괜찮다"고 판단하지 않습니다.
- 반대로 디자이너도 개발 제약(성능, 접근성, 재사용성)을 이유로 한 대안 제안을 존중하고, 필요 시 3자(기획 포함) 회의로 조정합니다.

## 5. 정기 미팅

- 주 1회 "디자인-프론트 싱크" (30분): 진행 중 화면의 Dev Ready 상태 확인, 토큰 이슈 공유
- 격주 "디자인시스템 리뷰": Hubkit 신규/변경 컴포넌트 검토
